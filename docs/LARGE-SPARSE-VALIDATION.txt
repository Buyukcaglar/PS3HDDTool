Units above use decimal TB, not TiB. The filesystem spans nearly the entire
logical image, excluding a 1 MiB prefix and 4096-byte tail. These are FULL-CAPACITY
allocation-map fixtures, not tiny filesystems followed by terabytes of padding.
All 7,451 target CGs, summaries and backup superblocks are authored and exercised.
Source payloads reach byte 999,924,633,599. Destination metadata/old payloads are
also authored at high offsets near 2 TB. Capacity/offset arithmetic is 64-bit.

The two image files together occupy 737,607,680 host bytes after the test, rather
than 3 TB. Each scenario retains TWO ~184 MB journals: successful migration and a
second interrupted migration recovered afterward. State/registry files need some
additional host space. No full-sized staging image is created inside the journal.
The journal measurement depends on this geometry/inode count; it is not a blanket
requirement for the user's formatted SSD. direct-plan reports the actual pair.
Peak RAM and elapsed time are process/fixture observations, not USB benchmarks.
The final CBC run overlapped other regression processes, unlike the earlier XTS
run; these durations cannot be used as crypto-mode speed comparisons.

What each full-capacity scenario checked
---------------------------------------
1. Mark each new REGULAR file sparse BEFORE extending it. Failure to set sparsity
   aborts, with no nonsparse fallback. Check actual sparse attributes/allocation.
2. Independently construct complete supported big-endian UFS2 geometry/maps for
   1 TB and 2 TB; place generated tree/old-target payloads near their far ends.
   Encrypt written metadata/payload sectors with generated derived keys. Originally
   free ciphertext holes remain sparse; free-sector plaintext is unspecified.
3. Fingerprint all host-allocated source ranges; plan read-only and confirm the
   target allocated-range fingerprint and journal nonexistence are unchanged.
4. Invoke production DirectMigrator.Run and reopen with DirectMigrator.Verify.
   Independently audit raw inodes, attributes, directory records/remapped links,
   symlinks, sparse topology, payloads, EAs, ALL CG bitmaps/summaries and totals.
   The oracle uses its own parser/checks through streamed 64-bit file reads.
5. Keep the successfully migrated tree as the existing target for a SECOND copy.
   Start a separate dotnet child, then Environment.Exit(73) immediately after its
   durable data-copy boundary. This bypasses catch/finally/handle disposal.
6. Confirm the target primary is dirty. Temporarily rename the generated source
   and key out of their request paths, then recover from target + journal alone.
   No huge-file Copy is used. Restore the source/key filenames afterward.
7. Compare restored metadata, allocated original payload and outside-volume raw
   hashes; run the independent full filesystem oracle again; confirm the source
   allocated-range fingerprint is unchanged. Check journal size equals its plan.

Limits
------
The 115-inode source has only 835,584 allocated bytes including directories,
indirection and EAs. This does not test transferring 1 TB of occupied games or
large real inode populations. Native fsck/newfs, actual console files/signatures,
PS3 boot/account/trophy/license acceptance, populated 2 TB reliability, USB media
identity and physical power-loss/disconnect behavior remain unqualified.
Generated metadata exercises the engine's supported layout, not every native
format field or firmware-specific interpretation. File-level sparse controls do
not exercise the raw device backend. Process termination leaves Windows alive.
No physical drive, real key, firmware source, qualification flag or original
review checkout was accessed/changed. git diff --check passes.
