Populated synthetic direct-migration stress -- completed 2026-10-12 local
=======================================================

Boundary
--------
Generated regular files, generated keys, generated registries and opaque generated
payloads only. No physical drive opening, enumeration, device query, real key or
console data. Production migration code is unchanged by this stress-test work.
This is a population/metadata and bounded-payload test, not a transfer of 1 TB of
occupied data and not PS3/USB/hardware qualification.

Reproduce from the local fork
-----------------------------
  dotnet build PS3HddTool.MigrationTests -c Release
  dotnet PS3HddTool.MigrationTests/bin/Release/net10.0/PS3HddTool.MigrationTests.dll --populated-stress all

Use plain, cbc192 or xts128 instead of all to select one case. The default small
regression suite does not launch these opt-in stress runs. Do not rebuild the
test executable while a test or its crash-test child is running on Windows.

Workload
--------
Full UFS allocation-map geometry in exactly 1,000,000,000,000-byte source and
2,000,000,000,000-byte destination sparse files, 3,726/7,451 cylinder groups.
44,123 inodes: 39,413 regular files, 4,614 directories and 96 symlinks.
16 synthetic accounts, 2,048 save sets, 1,536 trophy sets and 96 installed-game
trees. Each game has 256 small assets in eight directories, metadata, EBOOT,
extended attributes, an executable hardlink, a symlink, an empty file and archive.
Saves include PARAM.SFO/PARAM.PFD/ICON0.PNG/SAVE.DAT; trophies include TROPUSR,
TROPTRNS and configuration data. Each account has act.dat and 96 synthetic RIFs.
User ownership/timestamps vary. Case-sensitive names, Unicode, CON and an over
4-GiB sparse file exercise paths and 64-bit file sizes. These are opaque test
bytes, not valid/signed/licensed PS3 objects.

Plain archives are 80 MiB each plus a 123-byte tail; every UFS block is allocated,
including their zero-filled blocks. Nonzero game/block identity tags occur every
4 MiB and at the tail. They are NOT UFS sparse archives. To keep host use low,
the plaintext run uses a TEST-ONLY file backend that persists zero writes using
FSCTL_SET_ZERO_DATA on generated regular-file handles. It does not generate data
on reads: reopening through the normal production reader sees the same bytes.
All migration allocation/copy/hash/journal/commit logic executes, but zero writes
bypass the normal raw FileStream write and physical media traffic is unmeasured.
An overlap/stale-byte/read-only/bounds/flush/reopen regression checks this backend.
Microsoft API reference:
https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_zero_data

Encrypted runs use the ordinary production direct image path, generated CBC-192
or XTS-128 keys and 1-MiB archives with a tag in every block. This scales payload
down while retaining exactly the same population/file-tree shape. Ciphertext is
not compressible; no special zero backend is used in these runs.

Assertions per case
-------------------
Read-only plan creates no journal and does not change target allocated-range hash.
Complete direct migration; reopen/production verify; independent raw inode,
directory, payload, sparse topology, hardlink, EA, map and summary audit over the
whole destination filesystem. Source allocated-range SHA256 remains unchanged.
Second migration starts with the fully populated destination retained as old
data, then an actual subprocess exits at "Direct data copy durable" without
catch/finally. Dirty primary required. Recover with source/key paths unavailable;
check protected metadata/old payload/outside raw digest, independent oracle again
and unchanged source. Undo length must match plan; no staging image in journal.

Storage policy
--------------
New cases run sequentially. Generated image allocation is measured with the
file-level allocation API, plus journal/report lengths, at progress boundaries
and after recovery. A 6-GiB per-case host-space ceiling and 2-GiB per-image fixture
ceiling fail the test if exceeded. These are measured high-water samples, not
physical free-space reservation or a guarantee against an exhausted host disk.
After every assertion passes, only the two exact generated image files are
deleted; reports, state and undo evidence remain. Failed images are retained for
investigation. Existing artifacts from earlier requests are not deleted.
