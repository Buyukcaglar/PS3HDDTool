Populated end-to-end CLI sparse migration stress -- 2026-10-12 local
==================================================================

Reproduce (opt-in; default regression does not launch this stress):
  dotnet build PS3HddTool.MigrationTests -c Release
  dotnet PS3HddTool.MigrationTests/bin/Release/net10.0/PS3HddTool.MigrationTests.dll --cli-populated-stress all
Select plain, cbc192 or xts128 instead of all to run one mode; encrypted runs CBC
and XTS only. Do not rebuild while a harness/CLI child is running on Windows.

Scope and workload
------------------
Only generated regular files, generated keys, generated registry and payload
bytes. No physical endpoint enumeration, probes, opens, reads or writes. Sparse
file APIs operate exclusively on generated regular-file handles. No real console
data/keys or device paths are supplied to any command.

Every mode uses the unmodified production CLI as separate dotnet child processes,
with stdin closed, stdout and stderr redirected and stdout consumed continuously.
All image I/O uses the production direct image transport. No injected transport,
zero-compacting backend, fake CLI or simulated progress data is used.

Source is exactly 1,000,000,000,000 logical bytes, destination exactly
2,000,000,000,000, with complete UFS maps for 3,726 and 7,451 cylinder groups.
Allocated source payloads extend into the final cylinder group near the 1TB end.
This is full-capacity filesystem geometry with bounded occupied payload, not a
transfer of one terabyte of occupied data.

44,123 inodes: 39,413 files, 4,614 directories, 96 symlinks, plus hardlinks.
16 accounts, 2,048 save sets, 1,536 trophy sets, 96 installed-game-shaped trees.
Each game has 256 small assets, EBOOT, metadata, extended attributes, hardlink,
symlink, empty file and a tagged 1MiB archive plus tail. Each account includes
activation/RIF-shaped data. Ownership/timestamps vary; Unicode, case distinctions,
CON names and a sparse file larger than 4GiB are included. All three crypto modes
use the same reduced payload shape to keep the ordinary image path economical.
These are opaque generated bytes, not valid signed/licensed PS3 objects.

End-to-end assertions per mode
-----------------------------
1. CLI direct-plan: correct inventory and undo budget; no journal or image change.
2. CLI direct-run: JSON events arrive while process is alive; live direct-status
   reports copying without claiming liveness/undo verification. Phase counters
   stay monotonic, byte/inode counts finish before a distinct commit stage.
3. CLI direct-verify and independent streaming raw inode/directory/payload/link/
   EA/sparse/map/summary oracle over the whole 2TB geometry; source fingerprint
   unchanged and destination geometry retained.
4. A second copy into that populated target. The controller reacts to observed
   progress after at least half the inodes have been processed by launching CLI
   cancel to create a marker. Require exit 130, recoveryRequired false, rolled-back
   state, rollback progress, protected raw bytes restored and independent oracle.
5. A third copy into the populated target. At the observed durable-data-copy
   event, stop only that generated-image CLI child with Process.Kill. Require an
   unfinished journal, dirty primary and no terminal success/error event.
6. Rename the exact generated source/key away. Journal-only CLI status still
   works. Corrupt one undo byte, require CLI recovery exit 4 and structured
   integrity error without any destination change. Restore that exact byte and
   independently check the whole original journal SHA256.
7. CLI direct-recover with source/key unavailable; repeat recovery idempotently.
   Restore source/key paths. Require raw protected-byte digest restoration,
   independent oracle, CLI direct-verify of the original completed session, and
   unchanged source fingerprint.
8. Check all three undo lengths against their exact plans and checksums. Require
   no staging/full-image file in any journal. ConsoleRuntimeValidated stays false.

Monitor and storage policy
--------------------------
The controller validates every NDJSON envelope/sequence/runId/PID/timestamp,
monotonic elapsed time and phase counters, terminal ordering and error exit code.
It records progress/heartbeat counts, copy counters, phase order, event gaps,
process exits, and source/restored byte fingerprints. Persistent CLI event logs
must match captured stdout byte-for-byte, including the killed session.

Heartbeat interval 0.5s; progress interval 100ms. A 90s event-silence/30min command
watchdog fails the synthetic test and retains images. Heartbeats prove reporting
liveness, not advancing disk I/O. The intentional child stop is process-loss
testing, not physical power-loss or USB cache/flush qualification.

Cases execute sequentially. File-level allocated bytes for both sparse images,
plus host artifact lengths for the entire new run (including earlier case undo
files), are sampled about every 10s and at operation boundaries. The run ceiling
is 6GiB; the initial fixture ceiling is 2GiB per image. Samples are high-water
observations, not continuous tracking or a reserved-space guarantee.

After all assertions pass, release only that case's exact two generated images.
Retain all NDJSON captures, stderr, request/state/registry files, undo journals,
storage samples and reports. Failed images remain for investigation. Existing
artifacts from earlier tasks are untouched.
