Required facts before connecting/copying
---------------------------------------
Record source and destination model, label serial, exact capacity in bytes,
adapter/port, Windows PhysicalDrive number, reported storage-descriptor serial,
logical/physical sector sizes, and absolute UFS partition start in 512-byte sectors.
Record these in the host session folder. Numbers can change on reconnection.
Match physical labels and capacities as well as reported serials. USB descriptors
can identify the bridge rather than the SATA medium; serial+length is not an
independent guarantee of media identity. Duplicate/missing/unstable serials stop
this workflow. Never substitute an unverified number or guess a partition offset.

The source must be the original 1TB HDD; target the intended 2TB SSD, already
formatted by this same PS3 and cleanly shut down. The selected destination volume
must be at least as large as the selected source volume, with enough ORIGINALLY
FREE fragments and inodes for the whole source tree. Its existing tree is replaced.
Other destination partitions and its formatted geometry are retained.

Both endpoints need supported clean UFS2, matching block/fragment sizes, 512-byte
logical sectors, reported physical units 512..4096 with zero alignment offset,
and destination partition/fragments aligned to those units. Dirty maps, unsupported
features, bad references and inconsistent summaries are refused, not repaired.
Do not initialize, repartition or format either PS3 disk in Windows.

Use the verified same-console DERIVED HDD key: cbc192-bswap16 = 24 bytes with
native ciphertext pair swapping; xts128 = 32 bytes with the tool's swap handling.
Legacy cbc192 is unswapped and is not the verified CECHA00 format. By default a
48-byte eid_root_key or GUI combined format is refused. The explicit endpoint
KeyKind="eid-root" option now accepts an exact48-byte root file and derives the
HDD key in memory without exporting it. KeyKind omitted/"derived" retains the
24/32-byte format. Both endpoint modes and resulting HDD keys must match; no
autodetection/fallback occurs. See ROOT-KEY-CLI-VALIDATION.txt. No key values are
shown, fingerprinted or copied by this runbook.

Provide the genuine source-era and current-console 256KiB xRegistry.sys snapshots
as separate host files. Do not manufacture agreement by using one file for both
unless its provenance establishes that the flash state is unchanged. Source
registry mappings must cover every eight-digit HDD home user. On this project's
CECHA00/NAND console, xRegistry.sys is flash state. Copying home directories cannot
recreate missing XMB accounts. ConsoleStateRestoreRequired=true is an unresolved
account-state prerequisite; reconcile it separately before treating this as an
account-preserving migration. No command below writes console flash.

Keep keys, registries, requests, logs and undo on separate local PC storage, never
either migrating disk. Use a fresh session per attempt. Keep at least 2GiB of free
host headroom beyond planned undo.bin as an initial operating margin, then reassess
for the actual inode mapping/state/log size and copy duration. This is a suggested
margin, not a guaranteed total. Avoid sync folders, reparse paths and disk sleep;
use stable power/USB connections and close other tools holding the disks.

5. Cancellation from another process -- host marker only
--------------------------------------------------------
Set $Cli to the same DLL and $Session to the same session path in the other shell.
Do not choose a new marker; it must match the copy command exactly.

  dotnet $Cli cancel --cancel-file (Join-Path $Session 'cancel.flag') --json

Marker creation success means only that cancellation was requested. Wait for the
COPY process to finish: normal safe cancellation is exit 130, error event with
recoveryRequired=false, and journalPhase=rolled-back (or no journal if cancelled
before writes). A late request can lose the race to successful commit; use final
status. Ctrl+C in the copy terminal is an alternative graceful request. Do not
kill the process, unplug a drive, close its terminal or delete a marker mid-run.
Leave existing cancellation markers/evidence in their old session. A restart needs
a NEW session/journal/marker and starts copying from the beginning, not resuming.

6. Journal status and recovery -- never concurrently with copying
-----------------------------------------------------------------
Reading status alone is allowed while copying: it opens host journal files only.
Use the exact saved $Journal. Unique log names preserve earlier observations:

  $Tag = [DateTime]::UtcNow.ToString('yyyyMMddTHHmmssfff') + '-' + [guid]::NewGuid().ToString('N')
  dotnet $Cli direct-status --journal $Journal --json --event-log (Join-Path $Session "status-$Tag.ndjson")
  $StatusExit = $LASTEXITCODE

Status exit 0 is not migration success: examine result.Phase/recoveryRequired.
stateChecksumValidated=true checks state.json, not undo or the destination; status
cannot determine whether a process is running. Confirm the original copy process
has exited before any recover/retry/verification operation.

For unfinished state after interruption, exit 4 or failed rollback: keep the target
offline, preserve the entire journal, diagnose the error and resolve the cause.
Recover uses the saved destination path/serial and raw undo; the source, key and
registry originals are not needed. It WRITES THE DESTINATION and restores the
pre-copy filesystem, not the new migration. Do not invoke on a complete session.

  $Tag = [DateTime]::UtcNow.ToString('yyyyMMddTHHmmssfff') + '-' + [guid]::NewGuid().ToString('N')
  dotnet $Cli direct-recover --journal $Journal --json --event-log (Join-Path $Session "recover-$Tag.ndjson") --heartbeat-seconds 5 --progress-interval-ms 1000 2> (Join-Path $Session "recover-$Tag.stderr.txt")
  $RecoveryExit = $LASTEXITCODE
  $RecoveryExit | Set-Content -LiteralPath (Join-Path $Session "recover-$Tag.process-exit.txt")

Require actual exit 0 and terminal result.Phase=rolled-back. Recovery validates
undo integrity, identity/ranges and protected data before writing, then reads back
restored sectors. It ignores cancellation; do not pass --cancel-file or interrupt
it. If interrupted, retain everything and retry recovery after resolving the cause.
Already rolled-back recovery is idempotent. Do not edit state.json, repair hashes,
recreate undo.bin or format to bypass a refusal. Native drive numbers are saved:
if Windows renumbers a disk, the CLI has no recovery endpoint-override option.
Reconcile the saved mapping safely before recovery; do not hand-edit the journal.
A missing/unreadable state is recoveryRequired unknown, not proof of a safe target;
retain the snapshot folder and inspect it before deciding what to do.

Rollback restores old filesystem metadata and allocated payload, not every free
sector; partial new bytes can remain in unallocated space. It is not secure erase.
Completed migration cannot be rolled back with direct-recover. Keep the old HDD.

Exit handling reference
-----------------------
0: command succeeded; for status, saved phase may still be unfinished.
130: safe cancellation only with terminal recoveryRequired=false; inspect phase.
4 or recoveryRequired=true/null: keep target offline, retain journal, inspect and
recover unfinished work before retrying. Do not automatically loop/restart.
5: integrity failure; stop and diagnose, even if automatic rollback succeeded.
6: reporting failed; process exit takes precedence over delivered exitCode 0.
1/2: other/usage error; inspect error and saved state before deciding next action.
No terminal event/process loss: inspect status; never infer completion from percent.
