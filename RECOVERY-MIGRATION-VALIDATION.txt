Recovery-file and raw-filename preservation -- local fork, 2026-10-12
===================================================================

Implemented behavior
--------------------
Follow-up: TARGET-PRESERVATION-VALIDATION.txt documents explicit target archival
preservation and the newer 159-test regression. The source view described below
remains unchanged; target preservation is a separate, opt-in admission path.

Directory names are identified, compared, hashed and transferred using their
original byte arrays. Diagnostic labels escape bytes rather than decoding with
UTF8 replacement. Distinct invalid UTF8 names, valid replacement-character names,
literal percent sequences and valid Japanese names cannot collide in comparisons.

SourceRecovery="detached-directory" / --source-recovery detached-directory is an
explicit source-only option for image preparation and direct migration. Default
mode still refuses orphan allocations. It neither repairs nor writes the source.
The original source is opened read-only. A bounded 128MiB in-memory copy-on-write
view carries generated metadata and must pass a fresh strict inventory before use.

Qualification requires a clean supported UFS2 volume, exactly one initialized
all-zero allocated unreachable inode record, 1..128 singly linked regular orphan
files and exactly one unaccounted 4096-byte fragment. That fragment must fully
parse as a directory whose dot entry identifies the zero inode, parent is root2,
and canonical # plus nine-digit inode names reference every orphan exactly once.
The missing directory must explain exactly one directory-count difference in its
cylinder group. All other allocation ownership, bounds, links, sectors, free maps,
fragment-run summaries, cluster summaries and superblock totals must validate.
Extra allocations, ambiguous identities, malformed entries, dirty state or a
preexisting recovery-container name are refused before destination writes.

The view adds /.ps3hddtool-recovery containing every orphan regular file with its
original payload, inode attributes, external attributes and sparse topology.
Its generated container uses mode0700, UID/GID0 and zero timestamps. The original
container attributes and the cause of their loss remain unknown. Evidence files:
  original-directory.bin       exact original 4096-byte detached fragment
  original-inode.bin           exact original zero inode record
  original-root-directory.bin  original logical root directory bytes
  recovery.json                original root/orphan records, identity and hashes;
                               explicit generated-attribute/unknown-origin flags
Only the virtual root entry/link count and generated metadata change. The original
source bytes stay unchanged. Recovery metadata and root must fit direct-pointer
budgets. Capacity/undo planning includes the additional evidence/container.

The normal transfer hashes orphan payloads, verifies the resulting destination,
and uses the same journal/rollback rules. Destination-only recovery does not need
the source. Default null recovery fields are omitted from canonical serialization
to preserve compatibility with existing checksummed strict-mode journals.

Physical migration remains on hold
---------------------------------
No application write path has been exercised on either physical disk. The physical
destination still has its own unresolved recovery allocations and J/M/N/P test
corpus. Source recovery mode is deliberately never applied to the destination;
normal inventory still refuses that target. Successful root replacement would
retire the old target namespace, so it requires a separately qualified preservation
path before admission. Native raw writes, USB power loss, PS3 boot and acceptance
of actual accounts, saves, trophies and games remain unqualified.
