Target preservation and native read-only evidence -- 2026-10-12
==============================================================

Implemented and tested
----------------------
The target's clean but detached recovery directory is handled by an explicit
TargetRecovery="detached-directory" option, requiring TargetPreservation for
direct migration. Strict mode remains the default. Qualification accepts exactly
one all-zero allocated unreachable inode, 1..128 singly linked regular orphan
files, one unaccounted 4KiB directory fragment naming all those files, and exactly
one matching directory-count discrepancy. Every other allocation/reference/map,
summary, total, bound and cleanliness check must pass. This is an evidence-backed
interpretation of the original filesystem, not a physical repair or fsck bypass.

The preservation archive contains raw ciphertext for ALL allocated file extents,
indirect blocks, external attributes, the detached directory fragment, initialized
inode records, cylinder-group/backup-superblock metadata, summary tables, selected
volume prefix and all bytes outside the selected volume. It bundles the approved
target registry. Unallocated payload and uninitialized inode space are excluded.
It is a live-filesystem preservation archive, not a whole-sector forensic image.

Every chunk binds its disk offset, length and bytes with SHA256; the whole archive
and canonical manifest also have SHA256 checksums. Manifest publication follows
fsync and complete host readback against the live target. Migration independently
requires identical handle identity, capacity, partition, crypto mode, recovery
mode, derived range list and every archived byte. Archive/registry/manifest handles
deny writing and deletion throughout migration. Invalid, stale, missing, truncated,
duplicate-field or unknown-field manifests cannot authorize destination mutation.

Original target payload remains protected during copy. Its files are preserved in
the HOST ARCHIVE; they are not merged into the new console-visible source tree.
After successful migration the old target's inode/root metadata has been replaced.
Keep the archive and registry until all preservation requirements are satisfied.

CLI operations
--------------
  target-plan --request FILE --json
  target-preserve --request FILE --json --event-log NEWLOG --cancel-file NEWFLAG
  target-verify --preservation DIR --json
  target-export --preservation DIR --output NEWFILE --json

Request fields: TargetPreservation (host directory), TargetRecovery (none or
detached-directory). Inline equivalents: --target-preservation, --target-recovery.
The target commands use DirectRequest, including its source/journal fields; they
do not open source payloads. See CLI.txt for NDJSON, cancellation and exit codes.
An interrupted capture has no trustworthy completion marker and is never reused.
Choose a new archive directory after cancellation or failure.

target-verify and target-export need no disk/key. Export creates a NEW sparse host
image of the original disk's logical size, writes archived ranges and verifies
every written byte before publishing the final filename. Omitted free ranges read
as zero ciphertext. No physical restore command is provided. Completed migration
verification requires the archive; incomplete-session direct-recover can operate
without source/key/archive, using the separately verified metadata undo journal.
Recovery restores the original filesystem, not every formerly free disk sector.

CreateReadOnly permits an independently identity-checked read-only transport to
create a host archive with an in-memory derived key. It refuses writable inputs.
It does not relax DirectDisk's offline, identity, alignment or exclusive-access
requirements for actual migration. Its caller owns native handle validation.
