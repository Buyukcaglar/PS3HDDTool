Source hashing and copying performance review - 13 October 2026

Scope and isolation
-------------------
These changes are in the development copy only. The active verification-resume
operation uses its unchanged, separately pinned bin directory. No real source
payload was rehashed, no payload was recopied, and neither physical drive was
opened by the performance tests. The original HDD remains disconnected.

Source hashing
--------------
The preceding verification fix also accelerates source pre-hashing: both phases
call UfsVolume.Hash. It walks each indirect page once and combines physically AND
logically contiguous payload into reads up to 1 MiB, hashing exact zeros for holes
and only logical bytes of partial tails. The CBC transport retains its existing
128 KiB raw-read limit. No source hash, ownership or metadata checks are skipped.

A separate generated 64 MiB source test confirmed identical SHA256 against the
previous logical-block hashing loop, for plain and CBC192 with byte swapping:

                          Previous raw reads       Current raw reads
Plain                           10,219                      70
CBC192 with byte swap            10,219                     521

Copying
-------
The previous optimized writer still read source payload one 16 KiB block at a
time. TreeTransfer now reads contiguous allocated source runs up to 1 MiB, then
allocates/remaps each block exactly as before. Allocated tail padding remains
unchanged; source content comparison still hashes only logical bytes. Holes,
directories, extended attributes and inline links retain their existing handling.

TransferDataBuffer now holds up to 4 MiB of contiguous destination payload rather
than 1 MiB. Buffer publication remains explicit, before publishing the inode.
Cancellation/error disposal does not publish pending buffers. The pointer cache,
exclusive device ownership, journal write guard, native write-through flag,
transaction flushes, rollback and mandatory destination verification remain.
Span slices avoid allocating a separate array for every copied filesystem block.

Both repeated previous/revised pairs passed full filesystem comparison and the
independent fixture oracle. The fixture includes generated account/save/trophy
paths, game contents, a hard link, a sparse file, partial tails, an inline link and
extended attributes. Images were released after success; evidence was retained.
The reusable payload buffer costs an additional 3 MiB of managed memory.

These comparisons request Thread.Sleep(1) per raw I/O to expose call overhead.
Windows scheduling can round that delay upward. Their elapsed times are NOT a
physical-device throughput forecast. Counts and byte equality are the useful
performance/safety evidence. No sustained hardware speedup is claimed.

Assessment of the actual copy slowdown
-------------------------------------
The recorded real copy ran about 68.97 MB/s during its first partial hour,
38.16 MB/s during the next hour, then 28.25-29.16 MB/s for several hours,
including large ISO and game archives. The transfer algorithm and write-through
policy did not switch at the slowdown. This is consistent with a sustained device
write limit/cache or background NAND work, but it does not prove which mechanism
caused the drop. No drive-temperature/cache telemetry was collected that could
distinguish those causes. New batching removes identifiable application overhead;
it cannot promise to eliminate a NAND-level throughput limit.

Microsoft documents the durability/performance tradeoff of write-through and
cache flushes; Micron describes fast write caches ahead of slower NAND. Those
general descriptions do not diagnose this particular BX500 revision:
https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching
https://www.micron.com/about/blog/company/insights/from-data-to-decisions-why-ssd-write-cache-matters-to-ai-applications
